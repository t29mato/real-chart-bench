# GT issues export

**License: CC BY 4.0.**

`gt_issues.json` / `gt_issues.csv` list ground-truth (Starrydata digitized
XY data) entries that a **human has confirmed are wrong**, for use by
Starrydata maintainers cleansing the upstream dataset. Both files are
generated by [`scripts/export/gt_issues.py`](../../scripts/export/gt_issues.py)
from [`data/verified_pairs/registry.json`](../verified_pairs/registry.json)
— do not edit them by hand; regenerate with
`python scripts/export/gt_issues.py`.

## `llm_flagged` vs `human_confirmed`

`registry.json` records, for each `VerifiedPairing`, whether the pairing's
ground truth is under suspicion (`rejection_category: "gt_suspect"`) and, if
so, a review status (`gt_suspect_status`):

- **`llm_flagged`** — an automated/LLM check raised a suspicion. Nothing
  more. VLM (vision-language model) readings are themselves error-prone, so
  this is *not* evidence the ground truth is actually wrong.
- **`human_confirmed`** — a human looked at the source figure and the
  Starrydata curve and confirmed the ground truth is wrong.
- **`human_rejected`** — a human looked and the LLM's suspicion was
  unfounded; the ground truth is fine.

**Only `human_confirmed` entries ever appear in this export.** An
`llm_flagged` entry is a suspicion, not a confirmed error, and reporting it
here as a "GT issue" would misrepresent an unverified machine judgment as a
human-reviewed finding to whoever acts on this file. This is enforced in
code via `VerifiedPairing.is_confirmed_gt_error`
(`src/real_chart_bench/domain/verified_pairing.py`), not by an
easy-to-get-wrong ad hoc check — see
`src/real_chart_bench/usecase/gt_issues.py`.

When `human_confirmed` is 0 (the case as of this writing), the export is
still written — a valid, well-formed file with zero issues — rather than
omitted or filled with placeholder rows. `gt_issues.json`'s `summary` block
always reports how many `gt_suspect`-flagged entries exist in total and how
many are still awaiting human review (`llm_flagged`, not yet adjudicated
either way), so the review backlog stays visible even while the confirmed
list is empty.

## One-way export

This is a **one-way** export. Nothing in this repository reads from or
writes to `starrydata2.org` — real-chart-bench's responsibility ends at
producing these files. Reflecting a confirmed issue back into the
Starrydata2 dataset is a separate task, owned outside this repository.

## Row schema

Each issue row carries the Starrydata-side identifiers and evidence needed
to act on it without coming back to ask what was wrong:

| Field | Meaning |
|---|---|
| `paper_id` | Starrydata/manifest paper id |
| `figure_id` | Starrydata figure id (registry.json's grouping key) |
| `doi` | The paper's DOI, when known (`data/manifest/v0/papers.json`) |
| `properties` | The `(prop_x, prop_y, unit_x, unit_y)` pairs observed on the figure's ground-truth curve(s) in `data/verified_pairs/ground_truth.json`, deduplicated. Can be empty: that file only stores curves for `verified`/includable pairings, so a `rejected` gt_suspect entry's properties may not be found there. |
| `gt_suspect_status` | Always `human_confirmed` in this export (see above) |
| `verified_at` | Date the registry entry was last reviewed |
| `evidence` | Free-text account of what disagreed (long-form prose) |
| `axis_range_mismatch`, `point_count_mismatch`, `y_value_offset_magnitude`, `missing_series` | Structured evidence fields from `RejectionEvidence` (`src/real_chart_bench/domain/verified_pairing.py`), each optional — populated only where the evidence text actually supports it |

Starrydata's raw `*_curves.csv.gz` schema also carries a `sample_id`
column, but it is not preserved anywhere in this repository's committed
data (`data/verified_pairs/ground_truth.json`'s curve entries carry only
`x`, `y`, `prop_x`, `prop_y`, `unit_x`, `unit_y` — see
`src/real_chart_bench/adapter/starrydata_csv.py`), so no sample-id column
exists in this export either.
