当初の見積り 1,790図は**実測の歩留まりでは届かない**(論文の生存率を 0.90 と仮定していたが、

## 4. クロップ枠の復元 — **関門は不合格。ただし理由は2つあり、片方は撤回に値しない**

Stage 0 の中心だった作業は終わった(マージ済み)。結果は**合格しなかった**が、
内訳を分けて読む必要がある。

| | 件数 |
|---|---|
| `crops/` を指すエントリ | **124** |
| 元画像がリポジトリに**無い** | **115**(21論文) |
| 探せたもの | 9〜11 |
| → **枠が画素レベルで一致** | **全件** |
| → **ファイルのバイト列まで一致** | **4** |

**理由1: 元画像が無い(主因)。** 抽出済みの図が `data/verified_pairs/images/` に
commit されたのは18論文だけで、**git 履歴を見ても削除された形跡はない。最初から
入れていない**。元は gitignore された `data/raw/images/` にあり、このマシンには
5論文しか残っていない。
**つまり Phase 0 は Phase 2(PDF の再取得と再抽出)より先には回せない。
設計の段取りが逆になっている。**

**理由2: エンコーダのビルド差(7件)。幾何は正しい。** 復元した枠で元画像を切り直すと、
**復号した画素は完全に一致する**(私が4件を独立に確認した)。違うのは PNG のバイト列だけで、
IHDR もフィルタ済みスキャンラインも同一、deflate の出力だけが違う。
バイト一致した3件は、**たまたま 2026-09-30 にこの環境で切り直したもの**である。

**したがって「バイト一致」という関門は、クロップ手順ではなくエンコーダのビルドを測っている。**
主条件2を守っている不変条件は**復号した画素の一致**であり、`tick_calibration.json` の
座標はそちらに対して定義されている。エージェントは**勝手に基準を緩めず**、
基準どおり4件だけを記録して判断を上げた。これは正しい。

**司令塔の判断待ち**: 関門を「復号画素の一致」に言い直してよいか
(`figure-fetch-distribution.md` §10.3 item 0)。言い直せば、残るのは理由1だけになる。

**もう一つ**: 切り出しの語彙 `{box, rotation_deg}` では足りない。論文83のクロップは
元画像の**上下反転**であることがビット単位で確かめられ、元はモード `L`、クロップは `RGB` である。
反転は検出して報告するが**記録はしない** — 語彙を広げるかは設計判断。
