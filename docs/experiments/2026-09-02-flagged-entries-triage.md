# 「要注意」45件の仕分け — 大半は旧判定方式のノイズだった

実施日: 2026-09-02
生データ: [`2026-09-02-flagged-entries-triage.json`](2026-09-02-flagged-entries-triage.json)
関連: 設計 [§7.44](../design/benchmark-architecture.md)、[§7.47](../design/benchmark-architecture.md)、[§7.49](../design/benchmark-architecture.md)、[pairing-automation.md](../design/pairing-automation.md)

## 背景

目視監査スクリプトは、registry の `x_range`/`y_range` と印刷軸の目盛ラベル値から
単位換算ファクターを**フィット**し、min端とmax端で値が食い違うエントリを
「needs attention」として立てる。検証済み111件のうち**45件**が立っていた。

45件という数字は「検証済みの4割が怪しい」と読めてしまうため、実体を確定させた。

## 結果

| 分類 | 件数 | 意味 |
|---|---|---|
| `benign_range_past_tick` | **32** | 良性。registryのレンジが最外目盛の外に伸びているだけ |
| `unit_space_difference` | **11** | 正常。SI単位のまま残っている表示単位変換のバックログ |
| `gt_suspect` | **1** | **本物のGT疑義**(18759/12217) |
| `undetermined` | 1 | 判定不能(18869/18876) |

**45件中43件は誤りではない。** 「45件が要注意」という表示は、フィット方式が良性の
片側余白を吸収してしまうことによるノイズだった(§7.49 の構造的転換が対処する問題)。

## 系統的な原因

3つの同一論文クラスタが、それぞれ1つの軸決定を全パネルで使い回したことに起因する
(パネルごとの独立した偶然ではない):

- **paper 18668**(12件): x が常に 300–850K、印刷は 300–800K
- **paper 27759**(5件): x が常に [350 or 300]–1000K、印刷は 400–1000K
- **paper 3733**(6件): x が常に 450–900K、印刷は 500–900K

加えて、多数の単発エントリに共通する副次要因がある: **registry の端点がちょうど 0**
のとき(抵抗率・濃度・熱伝導率など、この分野では自然な物理的下限)、最初の印刷目盛が
0でない丸い数字だと、監査スクリプトの比による検査は構造的に一致を確認できない
(ゼロ除算)。よって常に「不一致」と報告される。17037 / 18869 / 34286 / 44283-38965
が該当する。これは §7.49 で比からアフィン写像に切り替える理由そのものである。

## 本物のGT疑義: 18759 / 12217

印刷y軸は 250–1250 Ω⁻¹cm⁻¹。4曲線のうち3本(611–1035 S/cm)は軸内に収まるが、
**curve1 だけが 6.6–10.3 S/cm** で、他の**ちょうど100分の1**である
(662.292 vs 66229.1、1028.72 vs 102872)。上流Starrydata側で1系列だけ S/m と S/cm を
取り違えた単位エラーであり、デジタイズ誤差ではない。

ペアリング自体は正しいため status は `verified` のまま、§7.48 のスキーマで
`rejection_category: gt_suspect` / `gt_suspect_status: llm_flagged` を付与した。
**`human_confirmed` ではない** — ちょうど100倍という関係は強い証拠だが、これはLLMの
読みであり、人間だけが昇格できる(§7.48)。

なお本件は**評価スコアを汚染している**: 描かれた4曲線を正しく抽出したモデルが、
100倍ずれた4本目のGTに対して減点される。人間確認後の対応が必要である。

## トリアージが拾えなかったもの(独立掃引で発見)

このトリアージとは別に、検証済み111件・208軸の全数掃引を行い、2件を追加で発見した。
いずれも上記45件の枠組みでは見えないものである。

1. **paper 446 の3図(8724/8725/8726)**: commit 31bd7e9 の表示単位移行で、y は
   正しく変換された一方、x は単位ラベルだけ `K` → `°C` に書き換えられ値が273.15
   ずれたまま残っていた。修正済み(registry と GT を同時にずらすためスコアは不変)。
   トリアージが見逃したのは、この3件がそもそも45件のフラグ対象に入っていなかったため。

2. **paper 17044 / 20740(2a inset)**: y_scale が `log` であるにもかかわらず、GT に
   **非正の抵抗率が3点**含まれている(-4.5e-4 〜 -1.6e-4 Ω·m)。対数軸に負値は
   プロットできず、抵抗率が負になることも物理的にありえない。軸レンジに対しては
   2.4% と小さいが、他の負値ケース(下記)とは質的に異なる。トリアージはこの
   エントリを `benign_range_past_tick` と判定しており、フラグの原因(余白)としては
   正しいが、この別問題は拾っていない。

補足として、「物理的に非負であるべき量に負値がある」ケースを全数で調べたところ
19件見つかったが、**17044を除く全件は軸レンジの0.2〜0.9%**に収まる、原点付近の
手動デジタイズのノイズであり、報告に値する誤りではないと判断した(18668のPower
factor、44283のZT など)。数を稼ぐために誤りとして計上しないこと。

## 教訓

「45件が要注意」のような数字は、**判定方式の欠陥がそのまま件数として現れる**。
仕分ける前にその数字を外部に出していたら、実際には43件が正常であるデータについて
「4割が怪しいベンチマーク」という誤った印象を与えていた。
