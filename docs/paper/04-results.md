## 4.3 順位として報告しない

本論文が主張するのは順位ではない。主表から読めるのは、桁の違う3つの層である。

- **クラウドの言語モデル(上位3モデル)**: 点 F1 0.97〜0.99(軸あり)
- **ローカル VLM**: 0.47〜0.72
- **専用モデル LineFormer と CV**: 0.02 以下

上位3モデル同士の差は 0.015 で、図1〜2枚分の違いにすぎない。

LineFormer と CV の点 F1 がほぼ0なのは、線を画素の列として密に出し、マーカーを1点として特定しないためである。再現率は 0.17〜0.26 あるが、
適合率は 0.01 以下になる。これは「実験点を特定していない」ことの正しい反映である(3.2)。

**summary_score は差を隠す.** LineFormer は summary_score 0.7482 で点 F1 0.006、Qwen3.5-9B(bf16)は 0.9215 で 0.470 である。
曲線距離では、線が正解点の近くを通り、系列の本数が合っていれば高い値が出る。

**位置誤差.** クラウドの上位3モデルの一致点の平均距離は軸レンジの 0.37〜0.42%(軸あり)で、注意深い人のクリック誤差として報告されている
0.1〜0.4%(3.3)と同じ程度である。ただし一致した点だけの平均であり、比べている相手も人のデジタイズそのものなので、
モデルが人と同等の精度だという主張にはしない。

## 4.4 合成図では読めるのに、実論文の図では読めない

合成図で学習したチャート専用モデルが実論文の図で低いとき、それがモデルの限界なのか、こちらの実験環境の問題なのかを分ける必要がある。
次の3段階で確かめた(design §7.75)。

### (a) この環境で論文の値が出るか

各モデルの論文と同じテストデータを、著者の採点コード(TinyChart の `eval_chart2table.py`。DePlot の `metrics.py` と同一の実装)を
無改変で使って採点した(`docs/experiments/2026-10-05-repro-published-scores.md`)。

| モデル | テストデータ | 論文の値 | この環境 |
|---|---|---|---|
| TinyChart@768 | ChartQA 表抽出 500問 | RMS-F1 93.78 | **RMS-F1 93.20** |
| DePlot | PlotQA test 500図 | RNSS 97.1 / RMS-F1 94.2 | **RNSS 97.27 / RMS-F1 94.52** |
| UniChart base-960 | ChartQA 表抽出 500問 | 91.10 / 94.01(表抽出向けに追加学習した非公開の重み) | RMS-F1 80.79(公開の重み) |

TinyChart と DePlot は論文の値を誤差の範囲で再現した。DePlot は、Hugging Face のプロセッサーの既定(パッチ上限 2,048)では
PlotQA で RNSS 93.1 / RMS-F1 83.9 にしかならず、4,096 にすると論文の値が出た。以降の DePlot の測定はすべて 4,096 である。
UniChart は公開されている重みが論文の表抽出の行とは別物なので、低いのは想定どおりである。Granite Vision は採点プロンプトが公開されておらず、
ChartGemma は表抽出の論文値がないため、再現は行っていない。

### (b) マーカー形式の合成図なら読めるか

材料科学の実験グラフは、線よりもマーカーで個々の測定点を示す図が中心である。そこで、既存の合成図データセットから
マーカー形式のものとして PlotQA test の dot_line 100図(CC-BY-4.0)を選び、実論文の図と同じ指標(点 F1、τ = 2%)で測った
(`docs/experiments/2026-10-05-synthetic-vs-real.md`)。合成図の正解は生成元の値で、誤差がない。

### (c) 実論文の図ではどうか

同じモデル・同じ設定で、実論文の94図(軸なし条件)を測った。Claude も同じ合成図で測った(design §7.80、軸なし条件、v3 プロンプトの
「published research papers」の語を外しただけの版)。

|---|---|---|---|---|
| Claude Opus 5.5 | エージェント | **0.975** | **0.985** | 1.01 |
| Claude Sonnet 5.5 | エージェント | 0.966 | 0.951 | 0.98 |
| Claude Fable 5.1 | エージェント | 0.944 | 0.968 | 1.03 |
| Qwen3.5-9B(bf16) | 汎用 VLM(単発) | 0.959 | 0.485 | 0.51 |
| DePlot | 合成図で学習 | 0.959 | 0.156 | 0.16 |
| Granite Vision 4.1 | 合成図で学習 | 0.947 | 0.287 | 0.30 |
| TinyChart-3B-768 | 合成図で学習 | 0.932 | 0.050 | 0.05 |
| UniChart base-960 | 合成図で学習 | 0.884 | 0.132 | 0.15 |
| ChartGemma | 合成図で学習 | 0.497 | 0.035 | 0.07 |
| Claude Haiku 4.5 | エージェント | 0.352 | 0.033 | 0.09 |

読み取り:

1. **合成図では、上位はほとんど差がない。** Claude の上位3モデルとチャート専用モデル・汎用 VLM の上位は、どれも 0.93〜0.98 に並ぶ。
   合成図だけで比べれば、DePlot(0.959)は Claude Fable 5.1(0.944)より上になる。
2. **実論文の図では、チャート専用モデルは合成図の 5〜30% まで落ちる。** 汎用 VLM の Qwen3.5-9B は半分に落ちる。
   Claude の上位3モデルは落ちない。
3. したがって、**合成図での成績は実論文の図での成績を予測しない。** 合成図のベンチマークで同点のモデルが、実論文の図では 0.16 と 0.98 に分かれる。
4. ChartGemma は合成図でも 0.50 と低く、表を出さずに説明文を返す図がある。表抽出の公式プロンプトがなく、こちらで用意したプロンプトを
   使っている影響の可能性がある。Haiku 4.5 は合成図でも 0.35 で、実論文の図と同じく系列の取り方で失敗している(4.6)。

注意点が2つある。PlotQA は公開データセットなので、評価したモデルの学習データに含まれている可能性を排除できない(7.10)。
また合成図の1図(fig_085)は全点が描画範囲の外にあり、図からは値が読めない。Opus 5.5 はこの図に一般知識から推測した値を入れ
(ラベルに推測と明記)、Sonnet 5.5 と Fable 5.1 は空の回答を返した。

## 4.5 軸の扱い — 範囲を与える、与えない、人が目盛を校正する

軸の情報の与え方を3通りにして、同じ80図で測った。

- **軸あり**: 各軸の値の範囲とスケール(線形 / log)を渡す(3.1)。
- **軸なし**: 範囲もスケールも渡さず、軸ごとの報告規則だけを渡す(3.1)。目盛はモデルが自分で読む。
- **目盛ピクセル位置あり(pixcal)**: WebPlotDigitizer で人が行う軸校正と同じ情報を渡す。各軸の目盛2本の、画像上のピクセル位置と値、
  スケール、画像サイズである。範囲は渡さない。人は目盛を4点クリックするだけで、点の抽出は AI が行う、という分担を想定した条件
  (design §7.76〜§7.78)。目盛の位置は94図すべてで用意した(85図はオーナーのレビュー済みの記録、9図はオーナーが Web 画面で入力)。

| モデル | 実行 | 軸あり | 軸なし | 目盛ピクセル位置あり |
|---|---|---|---|---|
| Claude Opus 5.5 | クラウド | 0.986 | 0.985 | 0.985 |
| Claude Sonnet 5.5 | クラウド | 0.971 | 0.951 | **0.982** |
| Claude Fable 5.1 | クラウド | 0.973 | 0.968 | 0.974 |
| Gemma 4 31B(8bit) | ローカル(Mac) | 0.722 | 0.731 | — |
| Qwen3.8-27B(8bit) | ローカル(Mac) | 0.658 | 0.661 | — |
| Qwen3.5-9B(bf16) | ローカル(RTX 4090) | 0.470 | 0.485 | 0.420 |
| Qwen3.5-9B(bf16)、2段階・画素座標 | ローカル(RTX 4090) | — | — | 0.017 |
| Qwen3.5-9B(bf16)、2段階・0〜1000 座標 | ローカル(RTX 4090) | — | — | 0.031 |
| Claude Haiku 4.5 | クラウド | 0.022 | 0.033 | 0.044 |
| LineFormer(事前学習) | ローカル(RTX 4090) | 0.006 | — | 0.033 |

(密でない80図、τ = 0.02。LineFormer の「軸あり」は画像全体を描画領域とみなして値に直したもの、「目盛ピクセル位置あり」は
同じ検出結果を目盛の位置で値に直したもの。)

読み取り:

1. **上位3モデルは、どの条件でも 0.95〜0.99 にある。** 目盛のピクセル位置を渡すと 0.97〜0.99 にそろう。Sonnet 5.5 は軸なしより
   0.031 上がった。Opus 5.5 と Fable 5.1 はもともと軸を自分で読めているので、ほとんど変わらない。
   **人が軸の校正だけを行えば、点の抽出は AI に任せられる。** デジタイズで時間がかかるのは軸の入力ではなく点のクリックなので、
   この分担は実務の手間をほぼ全部 AI に移す。
2. **Haiku 4.5 は校正を渡しても点を取れない**(0.044)。ボトルネックは軸ではなく、マーカーの検出と系列の分け方である(4.6)。
3. **単発の VLM は、ピクセル座標を渡すとかえって下がる**(Qwen3.5-9B: 0.485 → 0.420、回答なし6図)。エージェントは画像処理で
   マーカーのピクセル位置を測り、校正の式で値に直せる。単発の VLM には、画像内の正確なピクセル座標を出す手段がない。
   そこで、モデルにはマーカーの画像内の位置だけを出させ、値への変換は採点側で同じ目盛校正を使って行う2段階の条件を設けた
   (design §7.79。座標は画素と 0〜1000 の相対座標の2通り)。結果は**どちらもほぼ0**だった(画素 0.017、0〜1000 で 0.031。
   τ = 0.05 でも 0.064 / 0.100)。画素座標を求めても、多くの図で軸の数値(例: 320〜480 K)をそのまま出したり、画像の外の座標を出したりした。
   **この 9B の単発 VLM は、マーカーを画像内で位置づけられない。** 目盛を読んで値で答える方(0.485)がはるかに良い。
   人が軸を校正する分担が効くのは、画像処理で位置を測れるエージェントに対してである。
4. LineFormer は描画領域が正しくなると再現率が 0.166 から 0.863 に上がるが、点 F1 は 0.033 にとどまる。線を画素の列として出す限り、
   適合率は上がらない(6.3)。

**軸なし条件で何を測っていないか.** 軸なし条件では、軸表記の慣習(軸タイトルの ×10ⁿ、log10 値で印字された目盛、°C)を報告規則として渡している。
2026-09 に Claude 5 系で規則を渡さずに10図(現在の採点対象では8図)で比べたときは、summary_score が一様に 0.08〜0.13 下がり、
その低下は軸表記に罠のある図に集中していた。したがって正確な主張は次のとおりである。**目盛の位置と値を読むことは解けている。
軸表記の慣習を解釈することは、この測定では測っていない**(7.7)。

## 4.6 上位モデルを分けていたのは「どの線を拾うか」

v2 プロンプト(2026-10-01〜02)の実行では、Opus 5.5 が軸あり条件で13図の**図中の近似線(fit)も系列として出力した**(100図時点の集計、
design §7.66)。正解データ(Starrydata)はマーカーの点だけを持つので、近似線は余計な点として適合率を下げた。v2 は
「参照・比較曲線は含める」と書いたが、近似線の扱いを指定していなかった。

v3 プロンプトはこの1点だけを直した(測定点だけを出し、近似線・ガイド線・理論曲線は出さない)。結果は次のとおりである。

| モデル | v2 軸あり 点 F1(適合率) | v3 軸あり 点 F1(適合率) | v2 軸なし | v3 軸なし |
|---|---|---|---|---|
| Opus 5.5 | 0.951(0.932) | **0.986(0.991)** | 0.986 | 0.985 |
| Sonnet 5.5 | 0.953(0.960) | 0.971(0.977) | 0.973 | 0.951 |
| Fable 5.1 | 0.917(0.915) | 0.973(0.979) | 0.934 | 0.968 |
| Haiku 4.5 | 0.030(0.020) | 0.022(0.014) | 0.031 | 0.033 |

Opus 5.5 の軸ありの適合率は 0.932 から 0.991 に上がり、軸なしとの差は消えた。v2 で見えていた上位モデルの差は、読み取りの精度ではなく
プロンプトの不備から来ていた。

2026-09 の Claude 5 系(v2 以前のプロンプト、軸あり)は Fable 5 0.941、Opus 5 0.918、Sonnet 5 0.672、Haiku 4.5 0.039 だった。

**Haiku 4.5.** Haiku 4.5 は実行のたびに、非白ピクセルの連結成分を色でまとめる画像処理を自分で書き、1本の線を複数の系列に断片化する。
2026-09 の実行では予測系列数が実際の平均 3.10 倍になった。9月の10図サブセットで画像を直接読んだときは summary_score 0.8788 を出している。
**低いスコアは読み取りの失敗ではなく手法の選択である。**

**画像ツールの有無.** v3 の Sonnet 5.5 の初回は、サブエージェントの Python に画像ライブラリ(Pillow)がなく、全図を目視で読んだ。
この回答は診断行として別に採点した: 軸あり 0.963、軸なし 0.965(Pillow ありの公式行は 0.971 / 0.951)。上位モデルでは、
画像処理を書けるかどうかは点 F1 をほとんど変えなかった。

ここから導かれる注意がある。**これはモデルの測定ではなく、ツールを自由に使えるエージェントの測定である。** 同じモデルでも、実行ごとに
選ぶ手法と拾う線が変わる。ローカル VLM とチャート専用モデルはツールを使わない1回の推論なので、この点で条件が違う(3.8)。

## 4.7 再現性について

Haiku 4.5 の 2026-09 の実行は、出力ファイルが途中で3回変化し、完了報告がファイルの中身と一致しなかった(`data/llm_subset_rest/RUN_NOTES.md`)。
2026-10 の v2 の実行でも、軸ありの後半バッチは一度ピクセル単位の430万点を書いた後、自分で書き直して2万点の版に置き換えた。

この経験から、2026-10 の実行では次の手順を取った。

- 回答は終わったバッチから即座にリポジトリへ保存し、短いファイルで上書きしない
- 件数はエージェントの自己申告ではなく、ファイルの中身で確認する
