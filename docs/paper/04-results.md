# 4. 結果

測定した手法は6種類である。

- **クラウドの言語モデル(Claude)** — Opus 5.5 / Sonnet 5.5 / Fable 5.1 / Haiku 4.5。Claude Code のサブエージェントとして起動し、
  画像とタスクだけを渡した。手法(目視、拡大、自作の画像処理)は各エージェントの自由である。本章の主な数値は v3 プロンプト
  (2026-10-04、`scripts/eval/llm_run_v3_prompt.md`。測定点だけを出し、近似線・ガイド線・理論曲線は出さない)による。
  v2 プロンプト(2026-10-01〜02)と 2026-09 の Claude 5 系の実行は履歴として 4.6 に残す。
- **クラウドの言語モデル(GPT)** — GPT-6.1-Sol。OpenAI の Codex CLI を、オーナーの ChatGPT アカウント(Plus)でログインして動かした
  (API キーは使っていない、design §7.81)。Claude と同じ封印ディレクトリ・同じ指示文・同じ図で、推論レベルは medium に固定した。
  Codex のサンドボックスで、書き込みは作業ディレクトリの中だけ、ネットワークは遮断した。
  世代比較として GPT-5.5 も同じ条件で測った(完全自動 0.451、人が軸を校正 0.279)。GPT-5.5 は画像処理を使わず、縮小画像の一覧を
  見て全図の値を目測で打ち込んだ。人が軸を校正する条件でも、渡した校正を使わずに値を推測した(4.6)。
- **ローカル VLM** — Gemma 4 31B、Qwen3.8-27B、Qwen3.5-9B(いずれも 8bit、mlx-vlm、M3 Max のノート PC)と、
  Qwen3.5-9B(bf16 ほか、vLLM、RTX 4090)。v3 プロンプトからエージェント向けの文を除いた単発版で、1図1回の推論(詳細は 6.3)。
- **ローカルのエージェント** — Qwen3.8-27B(Q4_K_M、Ollama、RTX 4090)を、GPT と同じ Codex CLI から動かした。GPT の行と同じ封印ディレクトリ・
  同じ指示文で、画像処理のコードを書いて実行できる。機械の外には何も出ない。主条件2だけを測った(4.2、詳細は 6.3)。
- **合成図で学習したチャート専用モデル** — DePlot、TinyChart-3B-768、UniChart base-960、Granite Vision 4.1、ChartGemma(RTX 4090)。
  図を表に変換するモデルで、画像だけを入力に取る。
- **専用モデル LineFormer**(事前学習済み、RTX 4090)。線を検出するが軸を読まないので、人の目盛校正(主条件2)で値に直して測る。

学習を使わない画像処理(色や明るさで画素をまとめるだけの CV)は測定対象にしない。既存の学習済みモデル(LineFormer、チャート専用モデル)が
すでに下限を示しているためである(design §7.82 追記)。

全実行を同じ91図・同じメトリクスで採点し直している。モデルの回答は保存済みなので、再採点にモデルの再実行は要らない。

**条件は2つである**(design §7.82)。

- **主条件1「完全自動」**: 画像と、「印字されたとおりの数で答える」という全軸共通の1文だけを渡す。軸の範囲もスケールも渡さない。
  目盛はモデルが自分で読む(3.1)。
- **主条件2「人が軸を校正」**: WebPlotDigitizer で人が行う軸校正と同じ情報を渡す。各軸の目盛2本の、画像上のピクセル位置と値、
  スケール、画像サイズである。人は目盛を4点クリックするだけで、点の抽出は AI が行う、という分担を想定する(design §7.76〜§7.78)。
  目盛の位置は91図すべてで用意した(82図はオーナーのレビュー済みの記録、9図はオーナーが Web 画面で入力)。

軸の値の範囲だけを渡す条件(v0 以来の旧主条件)も測ったが、主条件にはしない。上位モデルでは、軸の範囲を渡しても渡さなくても成績が
変わらなかった(点 F1、範囲あり / 完全自動で Opus 5.5 0.986 / 0.985、Fable 5.1 0.973 / 0.968)。また「値の範囲は渡すが、画像のどこが
その値かは渡さない」という渡し方は、実際の使い方に対応しない。人が軸の情報を渡すなら、目盛の位置と値(主条件2)になる。

**時間とトークンについて.** 表の「秒/図」と「トークン/図」は、各結果ファイルの `run_cost` から取った(design §7.82 (3))。
どちらも「この実行のときはこうだった」という記録である。ローカルは機材、クラウドはその日の API の混み具合で変わる。

- 秒/図: クラウドのエージェントは、バッチごとの所要時間を足して図数で割ったもの。バッチは並列に動かしたので、実時間はこれより短い。
  ローカルは1図ごとの推論時間。RTX 4090 の vLLM は16図ずつまとめて推論したので、同じマシンの行どうしでしか比べられない。
- トークン/図: **数え方が提供元ごとに違い、提供元をまたいで比べてはいけない。** Claude は Claude Code がサブエージェントごとに報告する
  1つの数値(`subagent_tokens`)をバッチ分足したもの。Codex はキャッシュ分を含む全入力と出力を、すべての呼び出しにわたって足したもの
  (`total_tokens`)。ローカル VLM は入力と生成のトークン数の和。
- Claude の主条件1(v3)はオーナーの Mac で実行したので、ここには記録がない(記録なし)。チャート専用モデルはトークン数を記録していない。
  LineFormer は時間を記録していない。記録のない欄は推測で埋めない。

読み取り:

1. **Claude の上位3モデルは、校正を渡すと 0.97〜0.99 にそろう。** Sonnet 5.5 は完全自動より 0.031 上がった。Opus 5.5 と Fable 5.1 は

   かかるのは軸の入力ではなく点のクリックなので、この分担は実務の手間をほぼ全部 AI に移す。
2. **GPT-6.1-Sol は、校正を渡すとかえって下がった**(完全自動 0.978 → 0.861)。校正データの問題ではない。同じ校正で Opus 5.5 は

   (コンタクトシート)を見てピクセル座標を手で打ち込み、元の解像度に戻して校正式に入れていた。目測のずれがそのまま値のずれになる。
   完全自動では目盛の位置も同じ方法で測るので、ずれが打ち消し合う。Haiku 4.5 と同じく、**エージェントがどの手法を選ぶか**による
   失敗である(4.6)。
3. **Haiku 4.5 は校正を渡しても点を取れない**(0.044)。ボトルネックは軸ではなく、マーカーの検出と系列の分け方である(4.6)。
4. **単発の VLM は、ピクセル座標を渡すとかえって下がる**(Qwen3.5-9B: 0.480 → 0.434、回答なし6図)。エージェントは画像処理で
   マーカーのピクセル位置を測り、校正の式で値に直せる。単発の VLM には、画像内の正確なピクセル座標を出す手段がない。
   そこで、モデルにはマーカーの画像内の位置だけを出させ、値への変換は採点側で同じ目盛校正を使って行う2段階の条件を設けた
   (design §7.79。座標は画素と 0〜1000 の相対座標の2通り)。結果は**どちらもほぼ0**だった(画素 0.016、0〜1000 で 0.032)。
   画素座標を求めても、多くの図で軸の数値(例: 320〜480 K)をそのまま出したり、画像の外の座標を出したりした。
   **この 9B の単発 VLM は、マーカーを画像内で位置づけられない。** 人が軸を校正する分担が効くのは、画像処理で位置を測れる
   エージェントに対してである。
5. **ローカルのエージェントが GPT-6.1-Sol を上回った**(Qwen3.8-27B Q4、0.913 対 0.863)。同じ Qwen3.8-27B を単発で使った行は
   完全自動で 0.658 である(4.1。8bit で、主条件2は測っていないので条件も量子化も違う)。それでも差の大部分は、
   **ツールを使うエージェントとして動かしたこと**によると読むのが自然である。単発の VLM は校正を渡すとかえって下がる(読み取り4)。Claude の上位3モデルとは
   0.06〜0.07 の差があり、その約半分は回答のなかった図による。91図中5図(うち密でない図3図)で、モデルが「次にこれを調べる」という
   途中のメッセージだけを返してツールを呼ばず、再開3回の後も回答しなかった。全点見逃しとして採点している。回答した密でない74図だけでは
   Qwen 0.950、Opus 5.5 0.985、GPT-6.1-Sol 0.869 である(`results/qwen3.8-27b-v0-codex-local-pixcal.json`、`docs/design/local-model.md`)。
   ただし1図あたり約 17分かかる(6.3)
6. LineFormer は、検出した線を目盛校正で値に直すと再現率 0.858 に達するが、点 F1 は 0.033 にとどまる。線を画素の列として出す限り、
   適合率は上がらない(6.3)。

## 4.4 合成図では読めるのに、実論文の図では読めない

合成図で学習したチャート専用モデルが実論文の図で低いとき、それがモデルの限界なのか、こちらの実験環境の問題なのかを分ける必要がある。
次の3段階で確かめた(design §7.75)。

### (a) この環境で論文の値が出るか

各モデルの論文と同じテストデータを、著者の採点コード(TinyChart の `eval_chart2table.py`。DePlot の `metrics.py` と同一の実装)を
無改変で使って採点した(`docs/experiments/2026-10-05-repro-published-scores.md`)。

| モデル | テストデータ | 論文の値 | この環境 |
|---|---|---|---|
| TinyChart@768 | ChartQA 表抽出 500問 | RMS-F1 93.78 | **RMS-F1 93.20** |
| DePlot | PlotQA test 500図 | RNSS 97.1 / RMS-F1 94.2 | **RNSS 97.27 / RMS-F1 94.52** |
| UniChart base-960 | ChartQA 表抽出 500問 | 91.10 / 94.01(表抽出向けに追加学習した非公開の重み) | RMS-F1 80.79(公開の重み) |

TinyChart と DePlot は論文の値を誤差の範囲で再現した。DePlot は、Hugging Face のプロセッサーの既定(パッチ上限 2,048)では
PlotQA で RNSS 93.1 / RMS-F1 83.9 にしかならず、4,096 にすると論文の値が出た。以降の DePlot の測定はすべて 4,096 である。
UniChart は公開されている重みが論文の表抽出の行とは別物なので、低いのは想定どおりである。Granite Vision は採点プロンプトが公開されておらず、
ChartGemma は表抽出の論文値がないため、再現は行っていない。

### (b) マーカー形式の合成図なら読めるか

材料科学の実験グラフは、線よりもマーカーで個々の測定点を示す図が中心である。そこで、既存の合成図データセットから
マーカー形式のものとして PlotQA test の dot_line 100図(CC-BY-4.0)を選び、実論文の図と同じ指標(点 F1、τ = 2%)で測った
(`docs/experiments/2026-10-05-synthetic-vs-real.md`)。合成図の正解は生成元の値で、誤差がない。

1. **合成図では、上位はほとんど差がない。** Claude の上位3モデルとチャート専用モデル・汎用 VLM の上位は、どれも 0.93〜0.98 に並ぶ。
   合成図だけで比べれば、DePlot(0.959)は Claude Fable 5.1(0.944)より上になる。

   Claude の上位3モデルは落ちない。
3. したがって、**合成図での成績は実論文の図での成績を予測しない。** 合成図のベンチマークで同点のモデルが、実論文の図では 0.16 と 0.97 に分かれる。

## 4.5 順位として報告しない

本論文が主張するのは順位ではない。主表から読めるのは、桁の違う層である。

- **クラウドの言語モデル(Claude の上位3モデル、GPT-6.1-Sol)**: 完全自動で点 F1 0.95〜0.99
- **ローカルの汎用 VLM**: 0.48〜0.73
- **合成図で学習したチャート専用モデル、LineFormer**: 0.03〜0.29

上位同士の差は完全自動で 0.036 で、77図のうち数枚分の違いにすぎない。しかも同じモデルでも、条件によって選ぶ手法が変わり、成績が変わる
(GPT-6.1-Sol の主条件2、4.2)。

**そもそも、上位3モデルは現在の規模では順位づけできない。** 図ごとの点 F1 の対応のある差を取り、95% 信頼区間を出すと次のようになる(主条件1、密でない77図)。

| 比較 | 差 | 95% 信頼区間 | 判定 | この差を検出するのに必要な図数 |
|---|---|---|---|---|
| Opus 5.5 − Fable 5.1 | +0.0177 | [−0.0038, +0.0392] | **0 を含む** | 約 231 |
| Fable 5.1 − Sonnet 5.5 | +0.0183 | [−0.0139, +0.0504] | **0 を含む** | 約 487 |
| Opus 5.5 − Sonnet 5.5 | +0.0360 | [+0.0130, +0.0589] | 0 を含まない | 約 64 |

**隣り合う組はどちらも有意でなく、1つ飛ばした Opus 対 Sonnet だけが分離する。** 本節が順位を主張しないのは方針の問題ではなく、**データの分解能が足りない**ためである。

**指標を替えても順位は保たれない。** 同じ回答をチャート→表の指標で採点すると、点 F1 で1位の Opus 5.5 は `rms_f1_value_only` と `nms_f1` では4位に落ちる(4.9)。ただしこの入れ替わりは**指標の対応づけの取り方で決まる**ことを確かめており、モデルの優劣として読んではいけない(4.9)。順位は図数にも指標の選択にも依存する、というのがここで言えることである。

これは規模を増やす理由でもある。「他のベンチマークが大きいから」ではなく、**今の規模では測りたい差が測れていないから**である。必要な図数の見積もりは design `scaling-verification.md` にある(論文単位の級内相関が 0.46 に達するため、同じ論文から多数の図を採るより論文数を増やすほうが効く)。

LineFormer の点 F1 がほぼ0なのは、線を画素の列として密に出し、マーカーを1点として特定しないためである。再現率は 0.86 あるが、
適合率は 0.02 にとどまる。これは「実験点を特定していない」ことの正しい反映である(3.2)。

**summary_score は差を隠す.** LineFormer + 目盛校正は summary_score(91図)0.8885 で点 F1 0.033、Granite Vision は 0.9100 で 0.282 である。
曲線距離では、線が正解点の近くを通り、系列の本数が合っていれば高い値が出る。

**位置誤差.** クラウドの上位の一致点の平均距離は軸レンジの 0.37〜0.54%(完全自動)で、注意深い人のクリック誤差として報告されている
0.1〜0.4%(3.3)と同じ程度である。ただし一致した点だけの平均であり、比べている相手も人のデジタイズそのものなので、
モデルが人と同等の精度だという主張にはしない。

**軸表記の解釈.** 主条件1で渡す報告規則は、全軸共通の「印字されたとおりの数で答える」1文だけである。2026-10-06 に、正解データを
各図の印字どおりの表記に移した(log10 で印字された y 軸13本は log10 値、°C で印字された x 軸1本は °C、2.6、design §7.82 (2))。
それまでは、この14軸に図ごとの換算規則(10^値で答える、K で答える)を渡していた。既存の回答はその規則で答えているので、
採点時に逆変換している。点 F1 は全行で変わらなかった。軸タイトルにある倍率(×10⁴ など)は「掛けない」と共通の1文で指定しており、
この慣習の解釈は測っていない(7.7)。

## 4.6 上位モデルを分けていたのは「どの手法・どの線を選ぶか」

v2 プロンプト(2026-10-01〜02)の実行では、Opus 5.5 が軸の範囲を与えた旧条件で13図の**図中の近似線(fit)も系列として出力した**
(100図時点の集計、design §7.66)。正解データ(Starrydata)はマーカーの点だけを持つので、近似線は余計な点として適合率を下げた。
v2 は「参照・比較曲線は含める」と書いたが、近似線の扱いを指定していなかった。

v3 プロンプトはこの1点だけを直した(測定点だけを出し、近似線・ガイド線・理論曲線は出さない)。完全自動の条件で、v2 / v3 は
Opus 5.5 0.986 / 0.985、Sonnet 5.5 0.973 / 0.951、Fable 5.1 0.934 / 0.968、Haiku 4.5 0.031 / 0.033 である。
旧条件(軸の範囲を与える)では、Opus 5.5 の適合率が 0.932 から 0.991 に上がり、近似線の問題は消えた。v2 で見えていた上位モデルの差は、
読み取りの精度ではなくプロンプトの不備から来ていた。

**Haiku 4.5.** Haiku 4.5 は実行のたびに、非白ピクセルの連結成分を色でまとめる画像処理を自分で書き、1本の線を複数の系列に断片化する。
2026-09 の実行では予測系列数が実際の平均 3.10 倍になった。9月の10図サブセットで画像を直接読んだときは summary_score 0.8788 を出している。
**低いスコアは読み取りの失敗ではなく手法の選択である。**

**GPT-6.1-Sol.** 主条件2のバッチでは、マーカーを画像処理で検出せず、縮小したコンタクトシートを見てピクセル座標を手で打ち込んだ(4.2)。
完全自動では 0.978 で Claude の上位と並ぶので、これも読み取りの能力ではなく、その実行で選んだ手法の問題である。

**GPT-5.5.** 両条件とも画像処理を使わず、縮小画像の一覧と拡大図を見て、全図の値を目測で打ち込んだ。人が軸を校正する条件でも、
渡した校正を使わずに値を推測した。点 F1 は完全自動 0.451、人が軸を校正 0.279 である。同じく目測だけで答えた Sonnet 5.5
(Pillow なしの診断行)は 0.965 なので、低さは目測という手法そのものでは説明できない。この世代のモデルの、図から値を読む精度の差と考える。

**画像ツールの有無.** v3 の Sonnet 5.5 の初回は、サブエージェントの Python に画像ライブラリ(Pillow)がなく、全図を目視で読んだ。
この回答は診断行として別に採点した: 完全自動 0.965(Pillow ありの公式行は 0.951)。上位モデルでは、
画像処理を書けるかどうかは点 F1 をほとんど変えなかった。

ここから導かれる注意がある。**これはモデルの測定ではなく、ツールを自由に使えるエージェントの測定である。** 同じモデルでも、実行ごとに、
条件ごとに、選ぶ手法と拾う線が変わる。ローカル VLM とチャート専用モデルはツールを使わない1回の推論なので、この点で条件が違う(3.8)。

### 4.8.1 先行研究の値と並べるときの注意

ICPR 2020 Task 6b の実図の公開値は 0.710(IntSig-SCUT-Lenovo)と 0.232(DeepBlueAI)である。これが scatter の値なのか全チャート型の平均なのかは、手元の資料で確定できていない(下記、1.2 の脚注)。
Opus 5.5 の総合 0.757 はこれを上回り、4モデルとも 0.710 を上回る。しかし**これをそのまま「上回った」とは書けない**。
条件の違いは両方向にある。

- **本研究に不利な違い.** 先行の2行は上流タスクの正解(軸・凡例・文字)を与えたうえでのデータ抽出である。本研究の行は軸も凡例も自分で読む完全自動である
- **本研究に有利な違い.** 本研究の行は**ツールを使えるエージェント**で、画像を拡大し画像処理を書ける。先行の2行は畳み込みモデルの1回の推論である(7.3)
- **図の集合が違う.** 先行の値は ICPR 2020 の UB-PMC 評価セット、本研究は CHART-Info 2024 の**訓練セット**の scatter 582図である。同じ母集団からの別標本ではあるが、同一の図ではない
- **集計の単位が確定していない.** 本研究の採点ログ(`*.score.txt`)は先行の値を「全チャート型の平均で、scatter 単独の name / data の分解は未公開」と注記しており、データセット監査の記録は同じ値を scatter の行に置いている。原論文は今週は取得しない方針なので、確認は `docs/experiments/TODO-literature.md` の7に残した。全チャート型の平均なら、scatter 582図との比較はさらに弱くなる
- **データスコアだけで比べると並ぶ.** 名前の項(系列名の文字列一致、25%)を除いたデータスコアは Opus 5.5 で 0.705 で、0.710 とほぼ同じ水準である。
  先行の値が総合スコアなら、差のほとんどは系列名の項から来ている。4.8.4 の読み取り4のとおり、系列名の表記は読み取り能力と別の規約であり、
  **先行研究と比べるべきはデータスコアである**という本研究自身の基準に照らすと、「上回った」とは言えない
- **学習データの汚染.** CHART-Info 2024 の訓練セットは公開されている(7.10)。評価したモデルがその図や注釈を見ている可能性を確認していない

したがって本研究がこの表から言うのは、「6年前の最良値と**同じ水準**に、軸の正解なしの完全自動で届いた」までである。

### 4.8.2 失点の内訳 — 読み間違いと、正解データの書き方との食い違い

Opus 5.5 でも点 F1 は 0.887 で、本研究の77図(0.985、4.1)より 0.1 低い。この差が読み取り能力の差なのかを、
自動の失敗分析(`scripts/eval/analyze_chartinfo_errors.py`、各バッチの `error_analysis.{json,md}`)で分けた(design §7.86)。
図の特徴は正解データと注釈だけから機械的に付け、目視の判断は入れていない。

注意として、この分析の点 F1 は正解点の広がりで正規化しており(注釈の目盛を使う表の値より厳しい)、Opus 5.5 の582図平均は 0.873、失点は 0.127 になる。
特徴は「点ごとのラベル → 2本目の y 軸 → 密集」の順に最初に当たったものに数えた。

| 図の特徴 | 図 | Opus 5.5 の点 F1 | 全体の失点への寄与 |
|---|---|---|---|
| 点ごとのラベル(半数以上の系列が1点。凡例ではなく点ごとに名前が書かれた図) | 42 | 0.547(系列を無視すると 0.969) | 0.033(系列を無視すると 0.002) |
| 2本目の y 軸 | 23 | 0.530 | 0.019 |
| マーカーが密(3.4 と同じ基準) | 129 | 0.879(曲線 F1 で 0.917) | 0.027(曲線 F1 なら 0.019) |
| 上のどれにも当たらない | 388 | 0.926 | 0.049 |
| うち、log 軸もない図 | 350 | **0.937** | — |

**単位の書き方の分は、別に測った。** 回答の x か y の一方を、全系列まとめて 10ᵏ 倍(k = −9〜9)して採点し直し、最も良い点 F1 を取った
(`scripts/eval/chartinfo_rescale_gain.py`)。%目盛(×10⁻²)や ×10ⁿ の倍率の食い違いは、これで回復する。
読み間違いがたまたま 10ᵏ 倍で揃う場合も数えるので、**上限値**である。

| モデル | 回答どおり | 一方の軸を 10ᵏ 倍した最良 | 差 | 0.5 以上回復した図 |

読み取り。

1. **点ごとのラベルの図の失点は、ほぼすべて系列の分け方の食い違いである。** 正解データは、プロット内に名前が書かれた点を1点ずつ別の系列にする。
   モデルは値を正しく読んで1系列として返し、系列の1対1の対応で 0 近くまで落ちる(例: batch01 fig_29。2モデルが11点すべてを約 0.1 以内で読み、点 F1 0.091、`NOTES.md`)。
   系列を無視して点だけで数えると、この42図の Opus 5.5 は 0.969 で、寄与 0.033 のうち 0.031 が消える。
   この群で GPT-6.1-Sol だけが 0.929 と高いのは、点を1系列ずつに分けて返したためで、読み取りの差ではない

正解データが割合であることまでは確かめたが、図を見て1点ずつ照合してはいない。残る2図は説明がついていない。

**読み間違いでない失点は、どれだけか.** 上で測れたのは、系列の分け方 0.031、単位の書き方 0.014 以下、密な図の採点方式 0.008、
そして中身を分けていない2本目の y 軸の群 0.019 である。これらは測り方が違い(群全体の値と上限値が混ざる)、互いに重なりうるので、
足し合わせて「読み間違いはいくつ」とは書かない。言えるのは、**失点のかなりの部分は読み取り能力ではなく、正解データの書き方と採点方式に由来する**ということである。
そうした特徴のない図(350図)では、Opus 5.5 は 0.937、Fable 5.1 0.910、Sonnet 5.5 0.894、GPT-6.1-Sol 0.888 である。

これは 7.6 と同じ問題の、反対側からの観測である。Starrydata は図の全系列を持たないことがあり(`gt_incomplete`)、
CHART-Infographics は全系列を持つ代わりに**独自の書き方の規約**を持つ。どちらの正解データも、そのまま採点すると
読み取り能力ではないものを測る部分がある。

### 4.8.3 書き方に合わせたプロンプトは採らなかった

上の食い違いは、プロンプトで正解データの書き方を伝えれば消せる。実際に規則を作った(design §7.86、`data/chartinfo_pilot/prompt_v3.md`)。
テストセットに合わせ込まないよう、規則は評価に使う582図の task6 を一切見ずに、同じ ZIP のうち評価外で task6 を持つ 1,947図だけで決め、
評価外で 98% 以上一貫した規則だけを入れた(%目盛は割合、2本目の y 軸は左軸の単位、など)。design §7.86 の見積りでは全体で +0.03 前後になる(回し直していないので測った値ではない)。

**オーナー判断(2026-10-09)により、この v3 は採用せず、回し直してもいない。** 理由は、規則を評価外のデータから決めたとしても、
**正解データの書き方に合わせたプロンプト調整は「テストデータに合わせたプロンプトエンジニアリング」と読まれ、研究としての主張を弱める**からである。
本節の数値は v2(データセット固有の値の調整なし)のもので、上の食い違いは**失点の内訳の診断としてだけ**報告する。
v3 は不採用案としてリポジトリに残す。この判断の帰結は 7.5 に書いた。

## 4.9 別の指標でも同じ結果が出るか — チャート→表(RMS / NMS)での採点

4.8 は正解データを替えて測った。本節は**指標を替えて**測る。3.5.3 で、チャート→表の事実上の標準は RMS(DePlot)であり、
本コーパスには行見出しに相当するものが存在しないので RMS を主指標には使えないと述べた。それは文献調査からの議論だった。
本節はそれを**同じ回答に対する数値**にする。

採点側に3変種を追加し、主指標(点 F1)と**並べて**報告する(design §7.85)。保存済みの同じ回答・同じ正解データを使い、違うのは採点だけである。

- **`rms_f1`** — DePlot の RMS をそのまま実装した版。表を `(行見出し, 列見出し, 値)` の三つ組の集合と見て、行見出しに x の値、
  列見出しに系列名を置き、**見出しを文字列として**比べる(ANLS、text θ = 0.5)。値は `1 − min(1, |g−p| / |g|)`(number θ = 0.1)。
- **`rms_f1_value_only`** — 同じ対応づけのまま、見出しの項を無効化した版(一致した組の見出しスコアを1に固定する)。本研究が主として挙げるのはこの変種である。
  正解データの `series_label` は Starrydata の**データベース上の試料名**で、図の凡例が印字している文字列とは限らないため、見出しの文字列を採点に入れると
  「凡例とデータベース名が偶然一致した図」だけが得点することになる(オーナー判断、design §7.85)。
- **`nms_f1`** — `rms_f1_value_only` から、誤差の分母を `|g|` から**軸レンジ**に替えた版(対数軸は log10 空間)。PaperUnPlot の NMS(3.5.4)がしていることである。

**3変種はどれも y の値だけを数値として比べる。** x は見出しのテキストとしてしか現れず、数値としては照合されない。点 F1 は x と y を同じ尺度で見る(3.2)。
この構造の違いが、以下の数値のほとんどを説明する。

### 読み取り

**1. `rms_f1` が 0.26 で点 F1 が 0.985 になるのは、欠陥ではない。** RMS はセルの鍵を `(x の値, 系列名)` で作り、それを**文字列として**比べる。
連続な x の図では `320.02` と `320.0978` は、数値としていくら近くても文字列としては一致しない。本コーパスの正解データの x の小数桁は平均 4.28 桁で、
整数値なのは全体の 1.1% しかない。系列名のほうも、91図の 354 系列すべてが `series_label_source = sample_name`、つまりデータベース上の試料名である。

これは測定として出る。Opus 5.5 の完全自動では、**91図のうち 34図で `rms_f1` が厳密に 0** になる。同じ34図の `rms_f1_value_only` は平均 0.9241、
`nms_f1` は平均 0.9449 で、34図中 23図は点 F1 が厳密に 1.000 である。つまり**値は合っていて、見出しだけが一致していない**。
3.5.3 の「本コーパスには行見出しに相当するものが存在しない」という主張は、この 34図として測れる。

`rms_f1` が高く出る図を見ると、同じことが裏から確認できる。上位は 28331 の3図(0.833 / 0.810 / 0.803、系列名 `Lu0.1Bi1.9Te3` など)と
29352 の3図(0.754 / 0.751 / 0.721、`Bi0.5Sb1.5Te3-MW` など)で、いずれも**データベース上の試料名が、図の凡例が印字している組成式と一致している**図である。
0 になる図には `BaZr0.1Ce0.7Y0.1Ni0.1O3-delta Sintered at 1250dC - H2 (...)` のような、図のどこにも書かれていない記述が入っている。
`rms_f1` の図ごとの散らばりは、読み取りの精度ではなく、**データベース名が凡例と偶然一致したかどうか**を測っている。

**ただし、もっともらしい予想のうち確かめられなかった部分がある。** 「x の値が少なく丸い図ほど成績が良い」は、本コーパスでは成り立たない。

| 分け方(Opus 5.5、完全自動) | 第1三分位 | 第2三分位 | 第3三分位 | 順位相関 |
|---|---|---|---|---|
| 正解 x の小数桁が少ない順 → `rms_f1` | 0.2721 | 0.3443 | 0.1533 | −0.21 |
| 正解点の数が少ない順 → `rms_f1` | 0.1917 | 0.3256 | 0.2492 | +0.01 |

小数桁は弱く予想どおりの向き(桁が最も多い三分位だけが明確に低い)だが、桁が最も少ない三分位が最良にはならない。
点数のほうは**相関がない**。むしろ点数が最も少ない三分位は、`rms_f1_value_only` が 0.9484 とほぼ満点なのに `rms_f1` は 0.1917 で最も低い。
**x の桁数と点数のどちらも `rms_f1` を予測しない。** 効いているのは見出しの文字列が当たるかどうかで、x の項と系列名の項の両方が同じ向きに働いている。
2つの項の寄与を分離する測定は行っていない。

**2. `rms_f1_value_only` と `nms_f1` の差は、3.5.2 の比較そのものである。** 2つは分母だけが違う(`|g|` か軸レンジか)ので、
差はそのまま「正解値の大きさで割るか、軸の尺度で割るか」の効果になる。本研究が 3.5.2 で長く論じ、PaperUnPlot が独立に同じ結論に達した(3.5.4)点である。

差は**全10行で `nms_f1` のほうが高く**、+0.0186(Haiku 4.5)〜 +0.0919(Qwen3.8-27B)、平均 +0.070 である。
`|g|` で割ると、値が 0 に近い点で分母が小さくなり、同じ読み取り誤差が大きな罰になる。軸レンジで割るとこの依存が消える。

**図ごとに見ると一方向ではない。** Opus 5.5 の91図では `nms_f1 > rms_f1_value_only` が 66図、逆が 12図で、残り13図はほぼ同じである。
最大は 18668-12224 の +0.810(`rms_f1_value_only` 0.063 → `nms_f1` 0.873)で、この図の正解 y は ZT で、最小値が 0.00045 である。
`|g|` の 10% は 0 の近くでいくらでも厳しくなるので、読み取りが合っていても得点が入らない。
逆向きの最大は 4173-20121 の −0.411 で、こちらは正解 y(Seebeck 係数)が −46 〜 −55 に収まり 0 から遠い。
値が 0 から遠く、かつ軸の窓がその範囲に近い図では `|g|` の 10% のほうが軸レンジの 10% より緩くなり、向きが逆になる。
**分母の選択は、集計すると平均 +0.07 の一方向の差だが、個々の図では両向きに動く。**

**3. チャート→表の指標は、点 F1 と同じ順位を出さない。** これが本節で最も重要な観測である。

| 指標 | 上位4行の順 | 点 F1 の順位との Kendall τ(10行) |
|---|---|---|
| 点 F1 | Opus 5.5 > GPT-6.1-Sol > Fable 5.1 > Sonnet 5.5 | — |
| `rms_f1` | Opus 5.5 > Fable 5.1 > GPT-6.1-Sol > Sonnet 5.5 | **+0.956** |
| `rms_f1_value_only` | GPT-6.1-Sol > Fable 5.1 > Sonnet 5.5 > **Opus 5.5** | **+0.689** |
| `nms_f1` | GPT-6.1-Sol > Fable 5.1 > Sonnet 5.5 > **Opus 5.5** | **+0.733** |

**点 F1 で1位の Opus 5.5 が、`rms_f1_value_only` と `nms_f1` では4位になる。** 動いているのは2行である。

- **Opus 5.5(1位 → 4位)。** 原因として確認できたのは、まず**そうでないもの**である。(a) 密な図のせいではない。
  密でない77図だけで取り直しても `rms_f1_value_only` は GPT-6.1-Sol 0.9091 / Sonnet 5.5 0.8616 / Fable 5.1 0.8563 / Opus 5.5 0.8310 で、
  Opus は4位のままである(Fable 5.1 と Sonnet 5.5 は 91図と77図で入れ替わる。差は 91図で 0.009、77図で 0.005 で、どちらでも区別できない)。
  (b) 点の出し過ぎのせいでもない。Opus の予測点は 9,624 点で正解 7,061 点の 1.36 倍(全行で最多。
  GPT-6.1-Sol 1.19 倍、Fable / Sonnet 0.92 倍)であり、RMS の適合率は予測した三つ組の数で割るのでこれは直接効くが、
  差が最も大きい図は**両モデルが同じ点数を出した密でない図**である。28331-28492 は Opus・GPT ともに予測 36 点・正解 36 点で、
  **どちらも点 F1 が 1.000**(全点が軸レンジの 2% 以内)なのに、`rms_f1_value_only` は Opus 0.5709 / GPT 0.9389、
  `rms_f1` は逆に Opus 0.4740 / GPT 0.1372 と、同じ図で2つの指標が順を**逆にする**。
  残るのは対応づけである。RMS は見出しの文字列が最も近い三つ組どうしを組にするので、`rms_f1_value_only` は見出しを**採点から**外しても
  **対応づけからは**外していない(design §7.85)。行見出しに使えるものがないコーパスでは、どの組が作られるかは
  「モデルが x をどう印字したか」で決まる。

  **この経路を切り分けた。** 値の得点(軸レンジ正規化)はそのままに、**対応づけだけ**を見出し駆動から値駆動に替えて測り直すと、
  順位は次のように変わる。

  | 対応づけ | 上位4行の順 | Opus 5.5 |
  |---|---|---|
  | 見出し駆動(現在の実装、DePlot に忠実) | GPT-6.1-Sol 0.794 > Fable 0.762 > Sonnet 0.760 > **Opus 0.728** | **4位** |
  | 値駆動 | Fable 0.830 > GPT-6.1-Sol 0.823 > **Opus 0.820** > Sonnet 0.785 | **3位** |

  **順位は対応づけの取り方で変わる。** したがって「Opus 5.5 が4位になる」は**モデルについての所見ではなく、
  この指標をこのコーパスに当てたときの性質**である。見出しに使えるものがない以上、見出し駆動の対応づけは
  ほぼ任意の組を作り、その上で値を採点している。**本研究はこの順位の入れ替わりをモデルの優劣として報告しない。**

  これは 3.5.3 の主張を別の角度から裏づけてもいる。RMS をこのコーパスに当てられないのは見出しを**採点できない**からだけではなく、
  見出しがないと**対応づけ自体が定まらない**からである。
- **GPT-5.5(9位 → 6位)。** 点 F1 0.4517 で下から2番目だが、`rms_f1_value_only` は 0.6836 で、点 F1 が 0.21 高い
  Qwen3.8-27B(0.6828)と並ぶ。GPT-5.5 は画像処理を使わず縮小画像を目測で読んだ(4.6)。その答えは `|g|` の 10%(number θ)の内側には入るが、
  軸レンジの 2%(τ)の内側には入らない。**点 F1 のしきい値は「おおむね合っている」という情報を捨て、RMS / NMS はそれを残す。**
  どちらが正しいという話ではない。本研究が点単位のしきい値を採るのは、材料科学の利用者に「何点が使えるか」を返す必要があるからである(3.2)。
  抽出値をそのまま使わず傾向だけを見る用途なら、段階的な指標のほうが情報が多い。
- **`rms_f1` だけは点 F1 とほぼ同じ順位になる**(τ = +0.956、入れ替わりは Fable 5.1 と GPT-6.1-Sol の1組だけ)。
  ただし 1. のとおり `rms_f1` の水準自体は見出しの偶然に支配されているので、**順位が一致したことを根拠に `rms_f1` を信用する理由にはならない。**

密でない77図だけで取り直すと、さらに1つ入れ替わる。`nms_f1` では **Gemma 4 31B(8bit)0.89999 が Opus 5.5 0.89932 をわずかに上回る**。
点 F1 では 0.7371 対 0.9849 で 0.25 離れている2行である。差は 0.0007 で、4.5 の信頼区間の議論を当てるまでもなく区別できない大きさだが、
**チャート→表の指標はこの2行を同じ水準に置く**。

**4. 2つの指標は同じ図集合で計算していない。** `table_metrics` は91図すべてを採点する。見出しでの対応づけは、
マーカーが密な図でも疎な図と同じだけ定まるので、3.4 の分離(密な14図を点の主表から外す)を当てる理由がない(design §7.85)。
一方 4.1 の主表は密な14図を外した77図である。**したがって上の表の点 F1 の列と残り3列は、同じ図集合の値ではない。**

向きは測れる。密な14図のチャート→表のスコアは疎な図より大きく低い(Opus 5.5 で `rms_f1_value_only` 密 0.5533 / 疎 0.8310、
Gemma 4 31B では 0.2859 / 0.8143)。したがって91図で計算した3列は、77図で計算した点 F1 に対して**低い側に引っ張られている**。
同じ77図で取り直すと3列はそろって上がる。

| 手法 | `rms_f1` 91図 → 77図 | `rms_f1_value_only` 91図 → 77図 | `nms_f1` 91図 → 77図 |
|---|---|---|---|
| Claude Opus 5.5 | 0.2554 → 0.2783 | 0.7882 → 0.8310 | 0.8573 → 0.8993 |
| GPT-6.1-Sol | 0.2202 → 0.2457 | 0.8657 → 0.9091 | 0.9222 → 0.9680 |
| Claude Fable 5.1 | 0.2526 → 0.2769 | 0.8227 → 0.8563 | 0.8938 → 0.9295 |
| Claude Sonnet 5.5 | 0.2006 → 0.2259 | 0.8136 → 0.8616 | 0.8829 → 0.9331 |
| Gemma 4 31B(8bit) | 0.1858 → 0.2122 | 0.7330 → 0.8143 | 0.8159 → 0.9000 |
| Claude Haiku 4.5 | 0.0168 → 0.0199 | 0.0935 → 0.1070 | 0.1121 → 0.1262 |

**図集合をそろえても 3. の順位の不一致は消えない。** Opus 5.5 は `rms_f1_value_only` で4位のまま、`nms_f1` では5位に下がる。ただし上で見たとおり、この不一致の出どころは対応づけであって図集合ではない。
図集合の違いは、チャート→表の数値を点 F1 より低く見せる効果を持つが、順位の不一致を作っているものではない。

**本節の位置づけ。** 以上は、本研究の点 F1 が優れていることを示すものではない。示しているのは、
**チャート→表の標準指標でこのコーパスを採点すると何が起きるか**である。`rms_f1` は、このコーパスでは読み取り精度をほとんど測っていない(1.)。
`rms_f1_value_only` と `nms_f1` は読み取り精度を測るが、点 F1 とは別の順位を出し、どちらが「正しい」順位かを本研究は決められない(3.)。
先行研究と数値を並べるときは、相手がどの指標を使っているかに応じて選び、3つとも併記する(4.8 の読み取り2と同じ方針)。
`rms_f1` は、DePlot の定義に忠実であることが比較可能性の条件なので、見出しの項を含んだまま報告する(design §7.85)。
