いずれも Claude Code のサブエージェントとして起動し、画像とタスクだけを渡した。手法(目視、拡大、
自作の画像処理)は各エージェントの自由である。全実行を同じ100図・同じメトリクスで採点し直している。

## 4.2 順位として報告しない

上位5行は 0.9698〜0.9848 の幅に入る。そしてこの幅を決めているのは読み取りの精度ではない(4.4)。
曲線距離が最も小さいのは表で5位の Opus 5.5(0.0186)である。

本論文が主張するのは順位ではない。**フロンティア言語モデルは、軸校正を与えられればこのタスクで
0.97〜0.98 に到達する**。素朴なCV(0.7366)や専用モデル LineFormer(0.7462)との差は、
言語モデル同士の差とは桁が違う。

## 4.3 軸校正を外すとどうなるか

2026-10 の4モデルを、全100図で軸範囲を与えない条件でも測った(3.1: 範囲もスケールも渡さず、
軸ごとの報告規則だけを渡す)。

| モデル | 軸あり | 軸なし | 差 | 図ごとの差が ±0.02 以内 |
|---|---|---|---|---|
| Claude Opus 5.5 | 0.9698 | **0.9849** | +0.015 | 85図 |
| Claude Sonnet 5.5 | 0.9833 | 0.9837 | +0.000 | 95図 |
| Claude Fable 5.1 | 0.9788 | 0.9820 | +0.003 | 83図 |
| Claude Haiku 4.5 | 0.5988 | 0.2788 | −0.320 | — |

**上位3モデルは、目盛を自分で読ませても落ちない。** 曲線距離もほぼ変わらない(Opus 5.5 は両条件とも 0.0186)。

2026-09 に Claude 5 系で同じ比較を10図(現在の採点対象では8図)で行ったときは、一様に 0.08〜0.13 下がった
(例: Opus 5 0.9900 → 0.9133)。その低下は**軸表記に罠のある図に集中していた** — 軸タイトルに置かれた
×10ⁿ、1000/T のような逆数軸、log10 値で印字された対数軸。今回はその慣習を報告規則として渡しているので、
残るのは目盛の幾何的な読み取りで、そこはボトルネックではないことが100図で確認できた。

したがって正確な主張は次のとおりである。**目盛の位置と値を読むことは解けている。軸表記の慣習を解釈する
ことは、この測定では測っていない**(規則として与えた)。完全なエンドツーエンドの軸読み取りではない。

軸なし条件で例外的に大きく落ちる図は、クロップの際に目盛ラベルが切れて写っていない図である
(44283-39575 など)。モデルは同じ論文の別の図から軸を推測していた。この条件では原理的に解けない(7.6)。

## 4.4 上位モデルを分けているのは「どの線を拾うか」

Opus 5.5 が軸あり条件で5位なのは、13図で**図中の近似線(fit)も系列として出力した**ためである。
正解データ(Starrydata)はデータ点だけを持つので、近似線は誤検出として計上される。これだけで −0.0215、
除けば約 0.991 になる。同じ Opus 5.5 が軸なし条件では近似線を出しておらず、首位になった。

これはプロンプトの不備である。プロンプトは「参照・比較曲線は含める」と書いたが、近似線の扱いを
指定しなかった。モデルの能力差として読んではいけない。

9月の実行でも同じ構造が見えていた。

| モデル(2026-09) | 予測系列数 / 実際(実行時の記録) | match_rate(n=100) |
|---|---|---|
| Opus 5 | 中央値 1.00 / 平均 0.99 | 0.9988 |
| Sonnet 5 | 中央値 1.00 / 平均 1.00 | 0.9975 |
| Fable 5 | 中央値 1.00 / 平均 1.00 | 1.0000 |
| **Haiku 4.5** | 中央値 2.50 / **平均 3.10** | **0.4683** |

Haiku 4.5 は2回とも、非白ピクセルの連結成分を色でまとめる画像処理を自分で書き、1本の線を複数の系列に
断片化した。2026-10 の軸なし条件では1図あたり平均約7系列(正解は約4)を出し、カバレッジは 0.21 だった。
9月の10図サブセットで画像を直接読んだときの Haiku は 0.8788 を出している。**低いスコアは読み取りの
失敗ではなく手法の選択である。**

ここから導かれる注意がある。**これはモデルの測定ではなく、ツールを自由に使えるエージェントの測定である。**
同じモデルでも、実行ごとに選ぶ手法と拾う線が変わる。

## 4.5 再現性について

Haiku 4.5 の 2026-09 の実行は、出力ファイルが途中で3回変化し、完了報告がファイルの中身と一致しなかった
(`data/llm_subset_rest/RUN_NOTES.md`)。2026-10 の実行でも、軸ありの後半バッチは一度ピクセル単位の
430万点を書いた後、自分で書き直して2万点の版に置き換えた。

この経験から、2026-10 の実行では次の手順を取った。

- 回答は終わったバッチから即座にリポジトリへ保存し、短いファイルで上書きしない
- 件数はエージェントの自己申告ではなく、ファイルの中身で確認する(全16バッチで一致した)
- プロンプトをリポジトリに保存する(`scripts/eval/llm_run_v2_prompt.md`)

公表値はすべて、保存したファイルから再計算できる。
