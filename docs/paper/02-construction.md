# 2. データセット構築手法

この章が本論文の中心である。構築の各段階が、実図ベンチマーク固有の障害に対応している。

## 2.1 ライセンスによる選別

**OpenAlex を一次索引**とし、`is_oa:true` かつ `primary_location.license` が CC-BY 系のレコードのみを候補とする。ライセンス欄が空の場合は Crossref の `license.URL` で裏取りする。

判定の実装で一点、実データから学んだことがある。当初の擬似コードは `license_id` だけを見ており、closed-access 論文(`is_oa=false`)でライセンス欄が空のケースを素通りで「要レビュー」に送っていた。実測で 500件中393件(78.6%)がこれに該当し、レビュー待ち行列が意味を失っていた。`is_oa=False` を最優先で弾くよう修正し、レビュー対象を本当に判断の要る13%(65/500)に絞った。

各レコードは `license_source`(openalex / crossref / manual)、`license_checked_at`、`license_evidence_url` を保持する。**最終的な91図はすべて CC BY** である。

**ライセンスは後から変わる。** 2026-10-07 に全件を引き直したところ、採点対象だった論文のうち1本(446、`10.1515/amm-2015-0104`)が、収集時の記録 `cc-by` に対して現在 Unpaywall / OpenAlex とも **`cc-by-nc-nd`** を返した。本リポジトリはこの図のクロップ(= **改変物**)を再配布しており、ND は改変物の再配布を禁じる。オーナー判断により**該当3図を採点対象から外し、画像ファイルも削除した**(n94 → n91、2026-10-07)。

ここから2つのことが要る。第一に、**収集時の判定を信じ続けてはいけない**。再確認を定期的に回す(`scripts/eval/recheck_figure_licenses.py`)。第二に、**改変物を配っているという自覚が要る**。本データセットの図の大半はパネル分割とクロップを経た改変物なので(2.4)、NC や SA は受け入れられても **ND は受け入れられない**。再配布可能な論文を数えるときにこの区別を落とすと、使える母数を過大に見積もる — 公開コーパスの NC 系 320 本のうち 228 本は ND である(docs/experiments/2026-10-07-license-rescreen.md)。

## 2.2 ペアリング — 図とデータの対応づけ

Starrydata の XY データには、それがどの論文のどの図から起こされたかの情報が付随する。しかし図番号の表記は揺れ、1本の論文に似た図が複数あり、パネル分割された図では対応が一意でない。

対応づけの検証は数値的に行う。候補の図画像から軸レンジを読み、Starrydata 側の XY データがその範囲に収まるか、曲線の本数が図の凡例と一致するかを突き合わせる。**この検証を通ったものだけを `verified` とする。**

## 2.3 157件から91件へ — 脱落の内訳

| 段階 | 件数 |
|---|---|
| レジストリ登録 | 157 |
| ペアリング検証で棄却 | −18 |
| verified | 139 |
| 採点対象から除外 | −48 |
| **採点対象** | **91** |

除外48件の分類:

| 分類 | 件数 | 意味 |
|---|---|---|
| `gt_incomplete` | 26 | 図の系列数 > 正解データの曲線数。全系列を正しく抽出した手法が「余計な曲線」として減点されてしまうため |
| `gt_mismatch` | 6 | 正解データが図と対応しない |
| `harness_limit` | 4 | 評価系の側の限界(クロップにx軸が写っていない等) |
| `gt_wrong` | 3 | 人手で確認した正解データの誤り |
| `no_markers` | 3 | マーカー(測定点)がなく線だけの図。点単位で評価するため外した(下記) |
| `axis_unreadable` | 3 | x 軸の目盛の数字が切り抜きで画像に写っておらず、人にも図から x を読めない(2026-10-05、design §7.77) |
| `license_restricted` | 3 | 論文のライセンスが収集後に `cc-by-nc-nd` に変わっており、ND は改変物(クロップ)の再配布を禁じる(2026-10-07、2.1) |

重要な区別が4つある。

**`gt_incomplete` は正解データの誤りではない。** 図に5系列あってデータが4曲線なのは、デジタイズした研究者が自分の研究に必要な4本だけを起こしたというだけのことである。上流に報告する対象ではない。しかし採点には使えない。

`gt_incomplete` のうち6件は、構築の最終段階(2026-10-01〜02)で見つかった。図に**他論文の参照線・比較系列**が描かれているケースである — 例えば 18869-18874 では、自論文の5系列に加えて他論文の ZrCoSb・TiCoSb の曲線が点線・一点鎖線で重ねられている。Starrydata はその論文自身のデータしか収録しないので、これらは原理的にデジタイズされない。発見の経路は2つあった。正解にない系列を言語モデルが揃って抽出したこと(4章)、そして結果の閲覧ページで図ごとに重ね描きを見たこと。オーナーの判断は「そこに線はあるのだから、正解にないのが間違い」であり、採点ルールは変えずに図を外した。欠けた系列を補足デジタイズして採点に戻す仕組み(出所を Starrydata と分けて記録する)は用意してあるが、今回は使っていない。

**除外と上流報告は別の操作である。** `gt_wrong` の3件は採点から外すが、`data/gt_issues/` への上流エクスポートは継続する。採点に使えないことと、誤りを報告しないことは違う。

**`license_restricted` は図にもデータにも問題がない除外である。** ペアリングも画像も正解データも正しく、欠けているのは我々の配布権限だけである。だから `rejection_category` は設定せず(`pairing` / `image` / `gt_suspect` のどれでもない)、上流への報告対象でもない。**ライセンスが元に戻れば、そのまま採点に戻せる。**

**`no_markers` は図の種類による除外である。** 主指標を点単位にしたとき(3.2)、人がデジタイズするのはマーカーだけという前提に合わせ、データセットをマーカーのある図だけにした(オーナー判断 2026-10-03)。線だけの図は3枚(22102-21245、22102-21246、4965-13164)で、このうち 4965-13164 は、元論文(PLOS ONE)の本文から、測定点ではなく計算した量を滑らかな線で描いた図と判断した。正解データの誤りではない。

## 2.4 パネル分割とクロップ

1枚の画像に複数のパネルが入っていると、単一の `x_range` / `y_range` で表現できない。3件(28020/40067、32593/40587、36305/45818)を、正解データが属するパネルだけに切り直した。

切断位置は**目視ではなく枠のインク検出**で決めた。プロット枠を構成する縦線を列プロファイルで検出し、パネルaの右枠とパネルbの左枠の間で切る。32593/40587 の場合、パネルaの枠が x=2395 で終わり、列 2475–2525 が完全に空白、パネルbの内容が 2550 から始まる。x<2500 で切った。

複数パネルが1つの軸空間を共有する図(5902/15113、3段パネルがx軸を共有)は、**このバージョンでは対象外**とした。9本の正解曲線が 2+5+2 でパネルにまたがり、正解データ側に系列ラベルがないため、どの曲線がどのパネルに属するかを推定するしかない。推定すれば正解データを壊す。図もデータも誤っていないので、`multi_panel_merged` タグを付けて将来の再導入に備える。

## 2.5 軸校正の出所

抽出タスクにはx軸・y軸の範囲を与える(3.1)。この範囲がどこから来たかを、レコードごとに `tick_range_source` として記録する。**91図中82図が人手レビュー済み**で、残る9図はオーナーが目盛校正の画面で目盛のピクセル位置と値を入力し、全正解点が画像内に収まることを確認した(design §7.77)。

軸校正の測定では方法論上の失敗を4回繰り返した。いずれも同じ形をしている — **候補の軸位置を「正解データの点がインクに当たる率」で採点していた**。これは測定対象そのものを最適化する操作で、当たり率が高い候補を選べば、その図は必ず良いスコアを出す。

採用した手順は、**正解データから独立な証拠だけで測る**というものである。印刷された目盛ラベルの等間隔性、反対側スパインのミラー目盛、目盛間隔の一貫性。当たり率は選択には使わず、測定後の確認にのみ使う。

## 2.6 単位空間の統一

構築上いちばん手間のかかった箇所である。Starrydata は全データを SI 単位で保持するが、論文の図はほぼ常に別の単位で印字する — µV/K、S/cm、1000/T、mΩ·cm。

これを放置すると、**図の軸を正直に読んだ抽出手法が、正しく読んだことで罰せられる**。2026-09-30 に30軸・29図を論文の印字単位へ移行し、不一致を0にした。

3種類に分けて扱った。

| 種別 | 件数 | 処理 |
|---|---|---|
| 線形軸 | 19 | 丸い10のべき乗(×1e6、×1e4、×1e3)。残差が [0.5, 2] に入るときだけ適用 — 目盛外マージンで説明できる範囲 |
| 対数軸 | 11 | S/m 対 S/cm。log10 が両端ちょうど +2.00 デカード |
| 誤検出 | 3 | 対数軸に実数値を印字しているだけ。手を付けない |

1件(47247/48871)は端点が +1.89/+2.62 と合わず、図を直接読んで決めた。軸は `log(σ (S cm⁻¹))` で、×0.01 すると正解データが log10 で −4.73〜−1.76 になり、プロットされた点の範囲と一致する。ズレは目盛外のマージンだった。

移行には漏れが1件あった。28331-28500 は縦軸に「σ×10⁴ (S·m⁻¹)」、目盛に 5.0〜7.0 と印字されているが、正解データは 50000〜70000 のまま残っていた(同じ論文の 28492 は印字どおり)。2026-10-02 の LLM 再実行で、規則どおり 5〜7 と答えたモデルがこの図だけ大きく失点したことで見つかった。印字どおりに直し、旧範囲を見せて得た回答には採点時に同じ係数を掛けている(生の回答ファイルは変えない)。

**この移行でスコアは1桁も変わっていない。** 当時のメトリクス(現在の参考指標、3.6)は正解データ自身のyレンジで正規化するため、予測と正解が共有する係数は打ち消される。データセットの読み方を変えて、測っているものは変えなかったという確認である。現在の主指標(3.2)は軸レンジで正規化するが、軸レンジも正解データと同じ単位で保存しているので、同じく係数は打ち消される。

**印字どおりの表記へ(2026-10-06).** 上の移行は単位の倍率だけを扱い、印字そのものが物理量と違う形の軸は残していた。log10 の値を目盛に印字した y 軸13本(図には −6、−1 と印字され、正解データは 10⁻⁶、10⁻¹ を保存していた)と、°C で印字された x 軸1本(4173-20121、正解データは K)である。この14軸には、抽出手法に図ごとの換算規則(10^値で答える、K で答える)を渡して辻褄を合わせていた。これは、正解データの表記に課題のほうを合わせていたことになる。オーナーの判断で、正解データの側を図の印字どおりにした(design §7.82 (2))。13軸は log10 値を線形軸で持ち、20121 の x は °C で持つ。レジストリの軸範囲と目盛校正の値も同じ表記に移した。Starrydata の元のデータベースは変更していない。物理量は log10 を外せば戻るので、情報は失われない。

これで報告規則は全軸で「印字されたとおりの数で答える」1文になった(3.1)。既存の回答は旧規則で答えているので、採点時にその軸だけ逆変換する(10^値 → log10、K → °C)。逆変換は厳密で、0以下の値のように変換できない点は、旧来どおり一致しない点として適合率の分母にだけ入る。**主指標の点 F1 は全行で変わらなかった。** 対数軸はもともと log10 してから正規化していたので、log10 値を線形軸で持っても正規化後の座標は同じになる。参考指標の summary_score は、この14図で少し動く。

## 2.7 バージョニング

除外の判断は継続的に更新される。スコアは常にどのデータセット版に対するものかを明示する必要がある。`dataset_version` は `select_verified_pairings` の返す件数から**導出する**(例: `v0-eval-pilot-n94`)。ハードコードした版数が更新に取り残され、古い実行と混同される事故を経験したためである。

この規律は実際に効いた。旧 LineFormer の測定は `v0-eval-pilot-n42-comparable-n38` を名乗っており、現行の行と**比較してはいけない**ことが版数から自明だった。現在の主条件1(完全自動)は `v0-eval-pilot-n94-noaxis`、主条件2(人が軸を校正)は `v0-eval-pilot-n94-pixcal`、合成図は `synthetic-plotqa-dot-line-n100-noaxis` として、それぞれ別表になる。軸の範囲を渡す旧主条件の結果(`v0-eval-pilot-n94`)はリポジトリに残すが、表には出さない。線だけの3図を外したとき(n100 → n97)も、目盛の読めない3図を外したとき(n97 → n94)も、版数が変わったことで旧い結果ファイルとの混同は起きなかった。
