# 6. 配備制約 — クラウドに出せないデータ

## 6.1 スコアが最も高い手法が、常に使える手法とは限らない

4章の結果は、クラウドの言語モデル(Claude、GPT)がこのタスクで点 F1 0.95〜0.99 に達することを示した。しかしこれらはすべてクラウド経由のモデルである。

デジタイズの実運用では、クラウドに送れない図がある。

- **公開前の論文** — 査読中・エンバーゴ期間中の図
- **共同研究先から受領した未公表データ**
- **CC BY でない論文の図** — 本ベンチマークのデータセット自体は CC BY のみだが、実作業ではそうでない図も扱う

この制約は「AI を使うかどうか」ではなく「**データがどこへ出るか**」の問題である。完全にローカルで動くモデルは、プライバシー上は画像編集ソフトで PNG を開くのと変わらない。

## 6.2 「ローカル」の検証

実際に確認すべき点が3つある。

**1. 本当にローカルか。** テレメトリ、クラッシュレポート、実行時の重みダウンロード(HuggingFace hub への通信)、自動更新チェック。ネットワークを遮断して動作するかを確認するのが唯一の検証法である。

**Colab はローカルではない。** 「クラウドに出せないデータ」を動機とする議論の証拠を Google のマシンで取れば主張が崩れる。そこで LineFormer は、旧測定で使った Colab ではなく、ローカルの GeForce RTX 4090 で測り直した。ローカル VLM は、重みを事前に手元のキャッシュへ取得したうえで `HF_HUB_OFFLINE=1` で実行し、推論中に hub へ通信しないようにした(6.3)。ネットワークを物理的に遮断しての確認ではない。

**2. 重みのライセンス。** データが外に出なくても、non-commercial / research-only の重みは「再配布するデータベースを作る」という下流利用を禁じている場合がある。図のライセンスに対して行っているのと同じ規律で、**評価対象ツールごとにライセンス列を持つべき**である。今回測ったローカル VLM 3種は、いずれも Hugging Face 上で Apache-2.0 と表記されていることを確認した。

**3. データ側の義務。** NDA やエンバーゴが禁じているのは通常「第三者への開示」であって「手元でどのソフトを動かすか」ではない。ローカル処理は通常許容される。実際に効いてくるのは、元論文の公開前に派生 XY データを公表してしまうことであり、これは AI の問題ではなく公開タイミングの問題である。

## 6.3 ローカルでの実測

### 汎用の画像対応 LLM(ローカル VLM)

ノート PC で動く公開重みの VLM を3種測った。

| 項目 | 値 |
|---|---|
| 機材 | Apple M3 Max、ユニファイドメモリ 128GB(ノート PC) |
| モデル | Gemma 4 31B(`mlx-community/gemma-4-31b-it-8bit`)、Qwen3.8-27B(`mlx-community/Qwen3.8-27B-8bit`)、Qwen3.5-9B(`mlx-community/Qwen3.5-9B-8bit`)。いずれも 8bit、リビジョンを固定 |
| 実行 | mlx-vlm。温度0(greedy)、thinking 無効、JSON スキーマによる制約付きデコード、最大 8192 トークン |
| ピークメモリ | Gemma 4 31B 約36GB、Qwen3.8-27B 約34GB、Qwen3.5-9B 約13GB |
| プロンプト | Claude の v3 プロンプトから、エージェント向けの部分(作業ディレクトリ、「Python を使ってよい」など)を除いた単発版。1図1回の推論で、ツールは使わない(`scripts/eval/local_vlm/prompt_v3/`) |
| 画像 | 元ファイルをそのまま渡す。Gemma 4 は画像のトークン予算を既定の 280 から 1120 に上げた |

主表と同じ密でない77図(点 F1、τ = 0.02)と密な14図(summary_score)の結果(v3 プロンプト、主条件1「完全自動」、`v0-eval-pilot-n91-noaxis`):

| 手法 | 点 F1 | 密な14図 | 回答なしの図 | 秒/図(平均) | トークン/図 |
|---|---|---|---|---|---|
| Gemma 4 31B | **0.737** | 0.6202 | 4 | 113.5 | 2,593 |
| Qwen3.8-27B | 0.658 | 0.8227 | 1 | 67.8 | 1,938 |
| Qwen3.5-9B | 0.481 | 0.6694 | 4 | 26.8 | 2,128 |
| (参考)Claude Opus 5.5、クラウド | 0.985 | 0.9781 | — | 記録なし | 記録なし |
| (参考)GPT-6.1-Sol、クラウド | 0.977 | 0.9784 | — | 25.7 | 54,344 |

「回答なしの図」は、応答が解析できなかった図(採点対象の91図中)で、全点見逃しとして採点した。大半は 8192 トークンの上限で出力が切れたものである。
秒/図は推論時間の合計を採点した91図で割ったもので(4章冒頭と同じ規則。中央値は n94 の時点で Gemma 4 31B 63.8秒、Qwen3.8-27B 47.0秒、Qwen3.5-9B 15.0秒)、1台のマシンで1モデルずつ動かした。
トークン/図は入力と生成の和で、クラウドの行とは数え方が違うので比べられない(4章冒頭)。

最良の Gemma 4 31B は、点 F1 で 0.74 である。クラウドの上位(0.95〜0.99)とは 0.2 以上の差があるが、
実論文の図でのチャート専用モデル(0.05〜0.28、4.4)や LineFormer(0.03、下記)とは桁が違う。τ を 0.05 に緩めると Gemma 4 31B は
0.896 まで上がる(4.1)。点の場所はおおむね見つけているが、位置の精度がクラウドの上位に届いていない。

条件の違いに注意が要る。Claude はツールを使えるエージェントとして、画像を拡大したり自分で画像処理を書いたりできた。ローカル VLM は1回の推論で、
ツールを使っていない。差のどこまでがモデルの差で、どこまでが実行形態の差かは、この測定では分けられない。

### ローカルのエージェント — Codex CLI + Qwen3.8-27B

上の単発の VLM とクラウドのエージェントの差には、モデルの差と実行形態の差が混ざっていた。そこで、クラウドのエージェントと同じやり方
— 画像処理のコードを書き、目盛から校正し、拡大して確かめる — を、**機械の外に何も出さずに**できるかを測った
(`docs/design/local-model.md`「ローカルエージェント」)。

| 項目 | 値 |
|---|---|
| 機材 | NVIDIA GeForce RTX 4090(24GB)、Linux。全層が GPU に載る(VRAM 20.8 GB) |
| モデル | Ollama の `qwen3.8:27b`(Q4_K_M、17 GB、Apache-2.0)を文脈 102,400 トークンにした版 |
| エージェント | Codex CLI 0.160(`codex exec --oss --local-provider ollama`)。推論レベルは GPT の行と同じ medium。オーナーの Codex 設定とは別の `CODEX_HOME` |
| サンドボックス | GPT の行と同じ。書き込みは作業ディレクトリ(と `/tmp`)だけ、モデルが実行するコマンドのネットワークは遮断。モデルへの接続は Codex 本体から localhost の Ollama へ |
| 図・指示文 | GPT の行と同じ封印ディレクトリと指示文(主条件2「人が軸を校正」)。10図の試行のあと、残りを12図ずつ7バッチ |

結果(主条件2、91図、点 F1 は密でない77図の macro、τ = 2%。`results/qwen3.8-27b-v0-codex-local-pixcal.json`):

| 手法 | 実行 | 点 F1 | 密な14図 summary_score |
|---|---|---|---|
| Claude Opus 5.5 | クラウド、エージェント | 0.984 | 0.975 |
| Claude Sonnet 5.5 | クラウド、エージェント | 0.981 | 0.968 |
| Claude Fable 5.1 | クラウド、エージェント | 0.973 | 0.970 |
| **Qwen3.8-27B Q4(Codex CLI + Ollama)** | **ローカル、エージェント** | **0.913** | **0.833** |
| GPT-6.1-Sol(Codex CLI) | クラウド、エージェント | 0.863 | 0.977 |
| Qwen3.5-9B(bf16) | ローカル、単発 | 0.434 | 0.560 |

- **やり方はクラウドのエージェントと同じだった。** 10図の試行のログでは、全図を画像閲覧ツールで見たあと、Pillow / numpy / scipy で
  色マスクと連結成分のライブラリを書き、図ごとの検出スクリプトを足し、拡大した切り抜きを56回見直した。目測で値を打ち込むことはしていない。
  作業ディレクトリの外を読んだコマンドはない
- **未回答が差の約半分を占める。** 91図中5図(密でない図は3図)で回答がなかった。モデルが「次にこれを調べる」という途中のメッセージだけを
  返してツールを呼ばず、Codex がそれをターンの終わりとして扱った。中立の文で同じセッションを再開したが(最大3回)、最後も同じ形で終わった。
  ローカルモデルに特有の失敗である。回答した密でない74図だけで比べると Qwen 0.950、Opus 5.5 0.985、GPT-6.1-Sol 0.869
- **密な図には弱い**(0.833。クラウドのエージェントは 0.97 前後)
- **遅い。** 8セッションの作業時間の合計は 92,624秒(25.7時間)、1図あたり約 1,018秒(約17分)。バッチごとに 2,364秒から 29,795秒まで
  ばらついた。出力は 12.3M トークン、入力は 638M トークン(うち 597M はキャッシュ)で、文脈 100k に対して自動要約が繰り返し起きた。
  10図の試行の時点で、GPT-6.1-Sol の同じ試行の約100倍の出力だった

**データを外に出せない場面で、クラウドの上位に近い精度がローカルで出る**ことを示した最初の行である。単発で最良だった Gemma 4 31B
(完全自動 0.737)とは条件が違うので直接は比べられないが、同じ Qwen3.8-27B の単発(完全自動 0.658、8bit)より 0.25 高い。
代わりに、1図あたり単発の約15倍(Qwen3.8-27B 単発は平均 67.5秒)の時間がかかり、未回答という新しい失敗が現れる。
主条件1(完全自動)は、用意はしたが測っていない。

### 量子化の影響 — RTX 4090

ローカルで動かすとき、メモリに収めるために重みを量子化することが多い。その影響を、Qwen3.5-9B で精度だけを変えて測った(design §7.75 (2))。
すべて同じ公開重み(`Qwen/Qwen3.5-9B`、リビジョン固定)から作り、プロンプト・JSON スキーマ・生成設定は Mac の v3 単発版と同じにした。

| 項目 | 値 |
|---|---|
| 機材 | NVIDIA GeForce RTX 4090(24GB)、Linux |
| 実行 | vLLM 0.30.0、torch 2.13.0+cu130、温度0、thinking 無効、JSON スキーマによる制約付きデコード、最大 8192 トークン |
| bf16 | 公開重みそのまま |
| FP8 | vLLM による実行時の変換(W8A8 dynamic) |
| 8bit(W8A16) | 重みだけ int8、四捨五入(round-to-nearest)、キャリブレーションなし、group 128。lm_head と画像エンコーダは量子化しない |
| 4bit(W4A16) | 同じ方法で int4 |

| 精度 | 点 F1(完全自動) | 回答なしの図 | 秒/図(平均) | トークン/図 |
|---|---|---|---|---|
| bf16 | **0.480** | 4 | 7.2 | 2,181 |
| 8bit(W8A16) | 0.472 | 5 | 5.9 | 2,287 |
| FP8 | 0.470 | 3 | 4.1 | 2,074 |
| 4bit(W4A16) | 0.398 | 4 | 4.7 | 2,155 |
| (参考)Mac の mlx 8bit | 0.481 | 4 | 26.8 | 2,128 |

(密でない77図、τ = 0.02、`v0-eval-pilot-n91-noaxis`。秒/図とトークン/図は合計を採点した91図で割った値。RTX 4090 の秒は16図ずつまとめて推論したときの1図あたりで、このマシンの精度間でのみ比べられる。)

**8bit はほぼ無損失である**(bf16 との差は 0.011 以内)。重みだけの8bit でも、vLLM の FP8 でも、Mac の mlx 8bit でも同じ水準になった。
**4bit(キャリブレーションなしの四捨五入)は約 0.08 落ちる**(0.480 → 0.398)。 4bit で使うなら、キャリブレーションのある量子化法との比較が要る(未測定)。

### 専用モデル — LineFormer

LineFormer(ICDAR 2023、事前学習済み)を、他の全手法と同じ91図で、ローカルの RTX 4090 で測った。LineFormer は線を検出するが、軸は検出しない。
そこで、検出したピクセル座標を主条件2の目盛校正(91図すべて)で数値に直したものを LineFormer の行とする(4.2)。

| 手法 | 点 F1(77図) | 再現率 | 適合率 | summary_score(91図) | 密な14図 summary_score |
|---|---|---|---|---|---|
| **LineFormer + 目盛校正** | **0.033** | **0.858** | 0.018 | **0.8885** | 0.7809 |
| (参考)LineFormer、画像全体を描画領域とみなして変換 | 0.006 | 0.165 | 0.003 | 0.7482 | 0.6578 |
| (参考)Claude Fable 5.1、人が軸を校正 | 0.973 | 0.972 | 0.978 | 0.9870 | 0.9703 |

旧測定では、検出したピクセル座標を「画像全体 = プロット領域」として数値に直していた。論文の図には軸の外側に余白・目盛ラベル・軸タイトルが
あるので、その分だけ値がずれる。目盛校正で直すと、再現率は 0.17 から 0.86 に上がる。LineFormer の線は実験点の上を通っている。
それでも点 F1 は 0.03 にとどまる。線を密な画素の列として出し、マーカーを1点として特定しないので、適合率が上がらない。曲線距離の
summary_score では 0.89 が出るが、これは線が正解点の近くを通っていることを示すだけである(3.6)。この行は「軸情報を人から与えた
LineFormer」であって、単独で完全自動に使える手法ではない。実行時間は記録していない。

ローカル環境での注意点が一つある。OpenMMLab の配布サーバ(`download.openmmlab.com`)が組織のプロキシ越しに届かず、旧測定と同じ版の
mmcv-full を入手できなかった。mmcv-full 1.7.2 をソースからビルドし、torch は 2.1.2+cu121 とした。合成図3枚のスコアは旧測定と
一致している(0.9166 対 0.917)。

#### 点だけの散布図では何も返さない

点を結ぶ線のない散布図では、LineFormer の検出候補の信頼度は最高でも 0.000〜0.048 で、採用しきい値 0.3 を大きく下回り、何も返さない(100図の時点で3図)。線と点の両方が描かれた図では 0.93 程度の信頼度で正しく検出する。LineFormer は線のインスタンスを切り出すモデルであり、点の列は想定外の入力である。本データセットは全91図がマーカーの図である。

### 合成図で学習したチャート専用モデル

DePlot、TinyChart、UniChart、Granite Vision、ChartGemma も RTX 4090 で動かした(4.4)。いずれもローカルで動き、論文の値を再現できた
モデルもあるが、実論文の図での点 F1 は 0.05〜0.28 にとどまる。データを外に出せない場面での選択肢にはならない。散布図専用の Scatteract は、
学習済みの重みが公開されていないため評価できない(design §7.68)。

## 6.4 配備制約の論拠として言えること

測定が揃ったので、6.1 の主張を数字で書き直せる。

- 配備制約は実在し、クラウド API を使えない場面がある
- その場面で**ノート PC で動く汎用 VLM(Gemma 4 31B、8bit)は完全自動で点 F1 0.74** を出す。クラウドの上位(0.95〜0.99)には届かないが、**事前学習済みの LineFormer(人の軸校正を与えても 0.03)や、実論文の図でのチャート専用モデル(0.05〜0.28)より桁違いに良い**。ピークメモリ約36GB で、GPU サーバーを必要としない。ただし1図あたり平均 114秒かかる(この実行の記録)
- **8bit 量子化はほぼ無損失**で、4bit(キャリブレーションなし)は約 0.10 落ちる(Qwen3.5-9B、完全自動)
- LineFormer の低さの内訳は「読めない」ではない。**軸を見つけない**こと(目盛位置を与えると再現率 0.17 → 0.86)と、**マーカーを点として出さない**ことである。前者は軸検出を組み合わせれば埋まる部分があり、後者は出力形式と学習データの問題である
- **ローカルでも、エージェントとして動かせばクラウドに近づく。** Codex CLI から動かした Qwen3.8-27B(Q4、RTX 4090 1枚)は、人が軸を校正する条件で点 F1 0.913 を出し、GPT-6.1-Sol(0.863)を上回った。Claude の上位(0.97〜0.98)との差の約半分は未回答の5図による。代償は時間で、1図あたり約17分かかる(この実行の記録)
- ローカル VLM とクラウドの差には、モデルの差と実行形態の差(ツールなしの1回推論 / ツールを使うエージェント)が混ざっている。目盛のピクセル位置を渡しても、単発の VLM は値を計算できずにかえって下がる(4.2)。マーカーの画像内の位置だけを出させて採点側で値に直す2段階条件でも、点 F1 は 0.02〜0.03 だった(4.2)。単発の VLM には、人の軸校正を活かす手段がない。

したがって、データを外に出せない場面での現実的な選択肢は、現時点では専用モデルではなく汎用のローカル VLM である。単発で使うなら、その精度は完全自動の結果をそのまま使える水準ではなく、人手の後編集(5章)を前提とした出発点になる。人が軸を校正し、ローカルのモデルをエージェントとして動かせば 0.91 に届くが、1図に十数分かかるので、急がない大量処理(夜間のバッチなど)に向く。
